# CordScribe 受け入れ記録

更新日: 2026-09-24。対象はRyzenホスト上の初回構成と、Discordサーバー `1053500294044074024` の会議チャンネル `meet-test`。発言本文やBotトークンはこの記録に含めない。

## 確認済み

| 項目 | 結果 |
| --- | --- |
| Botのビルド・自動試験 | `npm run check` 成功。15件。8話者のRAM管理、28秒分割、STT再試行、クラッシュ復旧、根拠ID検証、投稿再試行、30日削除、270分割の統合を含む |
| STT実機 | `large-v3-turbo`、`int8_float16` をGPUにロードし、16kHz PCMの転写APIで応答を確認。停止後のモデル解放も確認 |
| Ollama実機 | 既存 `qwen3.5:9b` の構造化JSON応答と根拠ID検証を確認。WhisperとのGPU切り替えを確認 |
| Discord権限 | 非公開の `dev` VCでBotの閲覧・接続、`meet-test`で閲覧・送信・添付・履歴閲覧を確認。Bot単独のVC接続はReadyに到達 |
| 短い実VC会議 | 約35.6秒、話者1人、確定発言1件。文字起こし結果は`COMPLETE`。全文添付と要約v2の投稿IDがDBに記録済み |
| 要約失敗からの復旧 | 初回はモデルが根拠IDのない決定を返して検証失敗。発言IDをJSON Schemaの候補に限定し、根拠1件以上を必須に修正。同じ会議で再生成したv2は検証・投稿とも成功 |
| 長文の段階的統合 | 270個の一次抽出を要する合成入力を使い、8段階を超えても統合が完了する自動試験を追加。実際の3時間会議の速度・品質は未測定 |

3時間10分〜5時間10分の合成会議5件を用いた追加評価では、実モデルで重要発言の取りこぼしと全文要約の失敗を確認した。詳細は[長時間会議の合成データ評価](long-meeting-benchmark.md)。実際のVCで3時間会議を行ったわけではない。

## Gemma 4の比較（合成会議、実機）

2026-09-24に同じ6発言、8,192トークン設定、JSON Schemaで比較した。これはモデル選定の予備測定であり、長時間会議の品質や停止後の所要時間を保証しない。

| モデル | 所要時間 | GPU配置 | 内容 |
| --- | ---: | --- | --- |
| `qwen3.5:9b` | 未計測 | 62% GPU / 38% CPU | 担当者IDの整合性検証に2回失敗 |
| `qwen3.5:4b` | 21秒 | 未計測 | JSONは有効。担当作業をTODOに入れられなかった |
| `gemma4:e4b-it-qat` | 46秒 | 100% GPU | JSONは有効。概要が定型文で、担当作業をTODOに入れられなかった |
| `gemma4:12b-it-qat` | 163秒 | 60% GPU / 40% CPU | JSONは有効。決定、TODO、未決事項を区別できた |

Gemma 4の2モデルはOllamaへ追加済みだが、CordScribeの稼働モデル設定は`qwen3.5:9b`のまま。12Bは6GB GPUに全量収まらず、3時間会議の多数の抽出に使うには遅い。E4Bは全量載るが、このサンプルの要約品質では切り替えを決められない。会議中に別サービスが異なるOllamaモデルをロードした場合、現状のBotは自分の設定モデルだけを解放するため、GPU競合の実機確認も必要。

E4Bに約4,839文字の日本語合成入力と実装のJSON Schemaを与えたところ、入力は2,334トークンだった（設定上限8,192）。これは1チャンクの目安を確かめた値で、話者数、語彙、統合結果によるトークン増加まで保証するものではない。

## 公開前に残る実機確認

- 本人の同意前に発言が登録されないこと、撤回後に購読が止まり未確定音声が破棄されることをVC操作で確認する。短い会議では同意は確認できたが、DB上で撤回は確認できていない。
- 退出・再入室とVC再接続を実機で確認する。
- 2〜8人相当の同時発話と既存チャットBotの同時利用を確認する。
- 代表的な1時間の会議で音声欠損・GPUメモリ不足がなく、停止後30分以内に全文と要約が投稿されることを確認する。
- 3時間を超える会議を想定した発言数で、STT待ち行列、256MiBの音声RAM上限、要約の入力枠・統合回数・内容保持、停止から投稿までの時間を測る。許容時間は測定結果を見て決める。
- 投稿された要約の内容と根拠が実際の会話に合っているか、人が確認する。

この条件を満たすまで本稼働の受け入れは保留する。`qwen3.5:9b`が1時間会議の性能・品質を満たさない場合は `qwen3.5:4b` で同じ試験を行う。
